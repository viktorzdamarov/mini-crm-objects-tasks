3. Как это устроено (без кода)

Руководитель заводит стройку (объект) и задачи, назначает исполнителя. Исполнитель в интерфейсе видит только свои задачи и те объекты, где он участвует. Чужие задачи не открываются — это же правило стоит в базе, не только на экране.

Задача идёт так: новая → в работе (берёт исполнитель) → на проверке → либо принята, либо на доработке с комментарием. С принятой дальше никуда. Прыгнуть, например, из «новая» сразу в «принята», нельзя.

Каждый шаг по статусу пишется в историю: кто, когда, откуда-куда, комментарий если был. Через обычный доступ приложения историю не переписать. Регистрация снаружи выключена.

4. Где ТЗ молчит — как сделал я

Роль лежит в profiles, подтягивается из user_metadata при создании пользователя в Auth. Статус меняется только через transition_task_status; прямой update status режет триггер. Постановщик может менять текст задачи и исполнителя, но не автора и дату создания.

Не успел / не делал: realtime, автотесты, отдельный экран «все задачи» для постановщика (смотрит по объектам). Sign-up в Supabase нужно выключить руками в кабинете — в README написал.

Если удобно — на созвоне покажу сценарий постановщика, исполнителя и попытку открыть чужую задачу по прямой ссылке.
